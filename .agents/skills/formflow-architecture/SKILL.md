# FormFlow Architecture

Применяй при выборе места для кода и границ ответственности в FormFlow.

## Сначала прочитай

- `docs/INDEX.md` и [docs/architecture.md](../../../docs/architecture.md) от корня репозитория. Спецификация содержит анализ текущей реализации, таблицу размещения классов и рекомендации по развитию. Различай существующие пути и рекомендуемые каталоги, которые ещё не созданы.
- Ближайший реализованный сценарий и его тесты. Для простого CRUD ориентируйся на Tenancy; для вложенных ресурсов — также на FormDefinition и Submissions.
- При реализации используй `formflow-feature` и `laravel-best-practices`, при изменении спецификаций — `project-documentation`.

## Выбери минимальную структуру

1. Определи владельца бизнес-правила среди `app/Modules/Identity`, `Tenancy`, `FormDefinition`, `Submissions`. Новый модуль оправдан самостоятельной ответственностью, а не появлением таблицы.
2. Размести транспорт в `Presentation`, данные и координацию операции в `Application`, независимые предметные правила в `Domain`, Eloquent и технические адаптеры в `Infrastructure`. Используй точные пути из таблицы в спецификации; не создавай каталоги заранее.
3. Для простого CRUD оставь существующий путь Request → DTO → Controller → Repository → Resource. Выдели `Application/Actions/<Verb><Subject>Action` с методом `handle()`, если сценарий координирует несколько зависимостей, содержит существенные бизнес-решения или переиспользуется разными транспортами. Не добавляй Action-переадресатор на каждый метод репозитория.
4. Новый класс оправдан самостоятельным правилом, границей интеграции, содержательным повторением или независимой причиной изменения. В остальных случаях дополни существующий класс либо выдели метод.

## Сохрани границы и расширяемость

- Чистый `Domain` не зависит от Laravel, Eloquent, HTTP и внешних слоёв. HTTP-валидация не должна оставаться единственным местом бизнес-инварианта, если операцию можно вызвать другим способом.
- Существующие контракты репозиториев в `Application/Contracts/Repository` возвращают Eloquent-модели. Учитывай этот компромисс; не вводи отдельную domain entity и mapper на каждую модель ради формального DDD.
- Для межмодульных бизнес-операций используй прикладную операцию/контракт владельца, сохраняя его инварианты. Не вызывай чужие контроллеры или конкретные репозитории. Существующие ORM-связи не требуют попутного переписывания; новые связи оценивай по необходимости, не наращивай циклы прикладных вызовов.
- Расширяй поведение через внедрение зависимостей и композицию; пример — `CachedWorkspaceRepository`. Вводи интерфейс для осмысленной границы или точки подмены, а не автоматически для каждого класса.
- `final` совместим с расширением через контракт/композицию; DTO могут оставаться `final readonly`. Наследование используй при конкретной потребности переопределения с понятным контрактом. Не снимай `final` массово и не делай все методы `protected` на будущее.
- Избегай универсальных BaseRepository, пустых сервисных слоёв и общего Shared без устойчивой общей семантики. Размер класса оценивай по ответственности, а не числу строк.

## Межмодульное взаимодействие

- Для нового взаимодействия модуль открывает явный публичный контракт в `Application`. Передавай идентификаторы, значения и DTO без Eloquent-моделей, Builder, relations и HTTP-типов, включая вложенные поля. Внутренние repository interfaces с ORM-типами не являются публичной границей автоматически.
- Чтение актуальных данных и обязательное действие с результатом выполняй явным вызовом публичного контракта. Событие используй для факта и независимых реакций; не маскируй обязательную команду событием и не требуй взаимодействия только через события.
- Не добавляй прямой доступ к чужим моделям, таблицам и конкретным репозиториям. Текущие исключения устраняй постепенно в затрагивающих их задачах; сохраняй поведение и ограничения доступа.
- Для сценария определи требуемую актуальность, границу транзакции и успеха, последствия ошибки. Проверка доступа должна учитывать актуальное решение Tenancy; отстающая проекция membership требует отдельного согласования модели отзыва доступа.
- Синхронный обработчик связан с вызвавшей операцией по ошибкам и времени выполнения. Для асинхронного определи повторы, идемпотентность, окончательный сбой и нужный порядок; не предполагай однократную доставку.
- Уведомления о сохранённых изменениях публикуй после commit. Если потеря события недопустима, используй надёжную публикацию, например transactional outbox; одного after-commit вызова для этой гарантии недостаточно. Не вводи инфраструктуру доставки заранее без потребности.
- Payload и семантика события — публичный контракт: без ORM/HTTP-объектов, с учётом совместимости потребителей. Размещение событий и обработчиков смотри в спецификации; событийная интеграция не требует Event Sourcing или CQRS.
- При постоянных взаимных вызовах и общих транзакциях пересмотри границы модулей. Не закрепляй неудачное деление сагами или цепочками событий. Абстракция должна решать реальную точку изменения, а не обеспечивать гипотетическую замену каждой технологии.

## Проверь решение

- У каждого нового класса есть понятная ответственность, владелец и путь; дополнительный слой решает конкретную проблему.
- Проверены provider bindings, авторизация и ограничения выборки. Перенос координации не нарушает транзакцию, декоратор репозитория или эффекты после commit.
- Сопутствующий рефакторинг ограничен задачей. Обновлены затронутая спецификация и проверки; итог различает рекомендации и реально выполненные изменения.
