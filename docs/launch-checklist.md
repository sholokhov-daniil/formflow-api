# План подготовки FormFlow к запуску

Дата исходной проверки: 2026-11-08.

Статус: план работ; перечисленные ниже новые возможности не реализованы и не являются согласованным публичным контрактом. Создание этого файла не означает их реализацию.

## Назначение и границы

Этот документ хранит задачи, зависимости и критерии готовности приложения к первому запуску. Рабочее предположение: внешний посетитель заполняет форму обратной связи на сайте, приложение сохраняет обращение, а участник соответствующего workspace может получить его и обработать. Если приложение предназначено только для внутренних пользователей или принимает запросы исключительно от доверенного backend, сначала скорректировать объём по задаче R01.

Документ не заменяет спецификации: точный HTTP-контракт принадлежит [OpenAPI](api/openapi.yaml), архитектурные решения — [архитектуре](architecture.md), последовательности бизнес-решений — единственным диаграммам-владельцам в [бизнес-логике](business-logic/overview.md). Здесь фиксировать задания и доказательства выполнения, а не создавать второй пересказ этих правил. При реализации обновлять канонические документы в том же изменении.

Исходное состояние подтверждено чтением маршрутов, Requests, Resources, репозиториев и соответствующих feature-тестов. Тесты при составлении плана не запускались. Наличие внешнего frontend, настройки работающей инфраструктуры и каналов доставки не проверены.

## Как выполнять и обновлять чек-лист

1. Перед началом прочитать `AGENTS.md`, `docs/INDEX.md`, спецификацию затронутого сценария и применимые скиллы. Выполнить `git status --short`, проверить относящиеся к задаче staged/unstaged изменения; сохранить чужую работу и не менять индекс без запроса.
2. Если существует `.ai/rules`, прочитать индекс, подходящие по путям правила и найти дополнительные правила по ключевым словам. Проверить ближайшую реализацию и её тесты.
3. Работать по идентификаторам R01–R14. Сначала закрыть зависимости; независимые части допустимо выполнять отдельно. Не приступать к зависимой реализации до ответа на открытый вопрос, который меняет доступ, бизнес-правила или HTTP-контракт.
4. `[ ]` означает «не завершено или не подтверждено», `[x]` — «реализовано и проверено». При частичной реализации отмечать только выполненные подпункты. Верхнюю отметку в сводке ставить лишь после всех обязательных подпунктов задачи.
5. Перед отметкой записать в разделе задачи: дату, ссылки на изменённые файлы/PR или коммит, точные команды проверок и их результаты, оставшиеся ограничения. Не отмечать задачу по наличию классов, миграций или документации без работающего сценария.
6. При неприменимости задачи зафиксировать причину и согласованное решение; не выдавать её за реализованную. Обновить условие запуска в R14, чтобы исключение было явным.
7. Для PHP применять `laravel-best-practices` и подходящие PHP-скиллы, для архитектуры — `formflow-architecture`, для функций — `formflow-feature`, для доступа — `formflow-tenancy`, для API — `formflow-api-contract`, для тестов — `formflow-testing` и `testing-best-practices`. Для сценариев применять `formflow-business-logic`; актуализировать и проверять Mermaid в документе-владельце.
8. До использования новых API пакетов подтвердить установленные версии через Composer/lock-файл и использовать Boost `search-docs`, когда реализация зависит от Laravel API. Этот план не предписывает версию PHP по одному `composer.json`.
9. Запускать узкие проверки затронутого поведения. После изменения PHP выполнять `vendor/bin/pint --dirty --format agent`, проверяя отсутствие посторонних правок. Не запускать разрушающие проверки на рабочей БД. Для выпуска нужен отдельный полный прогон из R14.

## R01. Согласовать границы первой версии

**Текущий пробел.** Спецификации описывают существующий CRUD, но не законченный продуктовый сценарий внешней обратной связи. Нельзя автоматически считать публичную страницу, анонимность, email или конкретные роли уже согласованными.

**Результат.** В этом разделе зафиксированы ответы, а точные согласованные сценарии и контракты добавлены в документы-владельцы с явной отметкой целевого состояния до их реализации.

- [x] Определить отправителя: доверенный backend сайта. Для Vue SPA допустима прямая работа с публичным токеном формы; он не является секретом. Не выдавать посетителю членство в workspace ради отправки.
- [x] Определить способ заполнения: внешний frontend; каждый интегрирующий разработчик отвечает за свою клиентскую реализацию и её информирование пользователей. Центральный frontend-репозиторий не задан.
- [x] Выбрать минимальные поля первой формы: имя, email и сообщение. Обязательность и точные ограничения значений уточняются в R03.
- [x] Определить правила доступа к внешней форме: отзываемый публичный токен, ограниченный чтением публичной схемы одной формы и созданием отправок в неё. В браузере токен считается общедоступным; административные операции и чтение отправок этим токеном недоступны. Секрет административной/серверной интеграции не передавать в браузер.
- [x] Определить динамическую загрузку публичной структуры формы из API.
- [x] Определить аудиторию обращений: все участники соответствующего workspace; новые роли не вводятся.
- [x] Выбрать ручную проверку участниками workspace. Уведомлений и гарантированного срока обнаружения нет; данные доступны для чтения через защищённый API.
- [x] Определить правила изменения формы после получения ответов: сохранять версии полей и связывать историю ответов с использованной версией. Не удалять исторические ответы при изменении или снятии поля с публикации.
- [x] Определить границы данных: имя, email и сообщение хранятся до удаления оператором; доступ имеют участники workspace. Каждый интегрирующий разработчик отвечает за информирование пользователей о сборе данных. Не собирать IP, User-Agent и другие метаданные автоматически без цели.
- [x] Зафиксировать исключения первой версии: без вложений, статусов обработки и самостоятельной регистрации.

**Приёмка:** следующая модель может определить отправителя, точку входа, набор поддерживаемых полей, получателя и границу успешной отправки без догадок. Незакрытый вопрос блокирует только зависимую часть работ.

**Согласованные решения (2026-11-08).** Отправки выполняются в контексте отзываемого публичного токена конкретной формы; для SPA токен доступен клиенту и потому не считается секретом. Его полномочия ограничены публичной схемой и созданием отправок. Для серверной интеграции секреты остаются на backend. Внешний frontend не входит в этот репозиторий: его реализует разработчик-потребитель по контракту FormFlow. Подробности целевых сценариев зафиксированы в документах [форм](business-logic/form-definition.md), [отправок](business-logic/submissions.md) и в плановом контракте [OpenAPI](api/openapi.yaml); точные маршруты и схемы запроса/ответа оформить в R02–R03 до реализации. Эти решения описывают целевое поведение и не означают, что публичный API уже доступен.

**Подтверждение выполнения:** все решения R01 согласованы и отражены в целевых сценариях. Реализация и проверка пользовательского интерфейса не проводились.

## R02. Разделить управление формами и внешнюю отправку

**Текущий пробел.** В [маршрутах](../routes/api.php) операции форм и ответов требуют HTTP Basic и membership. Публичной отправки и безопасной публичной выдачи структуры нет. Административный `FormDetailResource` содержит служебные поля и не является готовым внешним контрактом.

**Где работать.** `FormDefinition/Presentation/Http`, `Submissions/Presentation/Http`, их прикладные контракты, `routes/api.php`, при необходимости policies и providers. Защищённые административные маршруты сохранить. Сценарии-владельцы: [определение форм](business-logic/form-definition.md), [ответы](business-logic/submissions.md); HTTP-детали — OpenAPI.

- [x] Определить пути и HTTP-формы внешнего API; контракт и реализация отражены в [OpenAPI](api/openapi.yaml).
- Решение R01: использовать отзываемый публичный токен, ограниченный чтением схемы одной формы и созданием отправок. Он может быть доступен SPA в браузере и не является секретом; точные маршруты, формат токена и ответы остаются задачей R02.
- [x] Разрешать внешнему отправителю только чтение публичной схемы и создание обращения; публичного чтения/изменения/удаления обращений нет.
- [x] Определять форму по токену на сервере; parent/owner поля тела не используются.
- [x] Создать отдельный внешний Resource: название и безопасные атрибуты активных полей, без идентификаторов и административных настроек.
- [x] Выпускать 256-битный токен защищённым endpoint; при перевыпуске предыдущий становится недействителен, в базе хранится только SHA-256 hash. Отзыв очищает hash.
- [x] Разрешённые CORS origin задаются `FORMFLOW_CORS_ALLOWED_ORIGINS`; credentials выключены. CORS не заменяет токен.
- [x] Для неизвестного, отозванного и неактивного токена/формы возвращать одинаковый 404.
- [x] Получать коды активных полей и их ID через прикладной контракт FormDefinition; межмодульный запрос к чужой таблице не добавлять.
- [x] Добавить тесты выдачи/отзыва токена, membership, публичной схемы, разрешённой отправки без Basic, отказа для чужих полей, отсутствия публичного чтения, подмены родителя, сокрытия служебных данных и защиты управления.

**Приёмка:** выбранный отправитель получает только необходимый доступ, а административные данные и обращения workspace остаются закрытыми.

**Подтверждение выполнения (2026-11-08).** Добавлены защищённые операции выдачи/отзыва, Bearer middleware, публичная схема и создание отправки с атомарной записью значений; контракт зафиксирован в OpenAPI. Разрешённые origin берутся из `FORMFLOW_CORS_ALLOWED_ORIGINS`. ## R03. Валидировать ответы по определениям полей

**Текущий пробел.** `StoreSubmissionValueRequest` и `UpdateSubmissionValueRequest` проверяют присутствие `value`, но принимают любой JSON, включая `null`. Создание значения проверяет принадлежность поля форме и уникальность в submission; проверки типа и `required` нет. Типы перечислены в `FormDefinition/Domain/Form/FieldType.php`.

**Где работать.** Внешний Request/DTO и прикладная операция `Submissions`; получение схемы через контракт `FormDefinition`. Чистые повторяемые предметные правила размещать в соответствующем `Domain`, координацию — в `Application`. Не создавать универсальный движок правил без потребности первой версии. Владелец сценария — [ответы](business-logic/submissions.md).

- [ ] Согласовать, как ответы адресуют поля: стабильный `code` или ID. Проверить уникальность и запрет дубликатов в одном payload; не смешивать два способа без причины.
- [ ] Зафиксировать различия между отсутствием ответа, `null`, пустой строкой, строкой из пробелов, `false`, `0` и пустым массивом. Обязательные boolean/number не должны отклоняться из-за общей проверки на «пустое».
- [ ] Проверять наличие каждого обязательного активного поля, принадлежность всех переданных полей форме и выбранную политику неизвестных полей. Не принимать поле другой формы даже при существующем ID.
- [ ] Для каждого разрешённого в R01 типа определить допустимый JSON-тип, формат, нормализацию и пределы. Для текста — длину, для email — проверку формата, для чисел — допустимый диапазон и дробность, для дат — формат и часовой пояс, если эти типы включены.
- [ ] Сохранять версии определений полей после появления отправок и привязывать каждое значение к версии, по которой оно было принято; изменение схемы не должно менять смысл или удалять историю существующих отправок.
- [ ] Ограничить размер обращения, количество ответов и длину отдельных значений. Не полагаться только на ограничения клиентского интерфейса или БД.
- [ ] Для типов вне первой версии явно отклонять попытку внешнего заполнения либо не допускать публикацию таких форм. Не принимать произвольный JSON под видом поддержанного `file` или `select`.
- [ ] Возвращать ошибки, которые frontend может привязать к конкретному полю. Указать точные имена, схемы и примеры в OpenAPI.
- [ ] Определить, продолжают ли старые административные операции значений быть низкоуровневым CRUD либо используют те же ограничения. Согласовать совместимость; при сохранении CRUD не называть его завершённой отправкой и не запускать по нему уведомления о готовом обращении.
- [ ] Покрыть тестами валидный минимум, пропуск обязательного поля, неверный тип, превышение лимита, неизвестное/чужое поле, дубликаты, граничные значения `0`/`false`/`null`, неподдержанный тип. Для отказов проверить отсутствие записанных частей обращения.

**Приёмка:** некорректное обращение отклоняется до сохранения; все разрешённые типы имеют проверяемые правила, а тип в определении поля влияет на приём ответа.

**Подтверждение выполнения:** пока не заполнено.

## R04. Сохранять заполненную форму одной атомарной операцией

**Текущий пробел.** `SubmissionRepository::createForForm()` создаёт только submission, а значения сохраняются отдельными HTTP-запросами. Нет операции завершения; сетевой сбой между запросами оставляет неполное обращение.

**Где работать.** `Submissions/Application` — DTO и координирующий Action, `Infrastructure/Repository` — сохранение, `Presentation/Http` — транспорт. Проверить контракты репозиториев и bindings в `RepositoryServiceProvider`. Владелец — [ответы](business-logic/submissions.md).

- [ ] Создать отдельную операцию приёма всех ответов выбранной формы. Имена классов подобрать по существующим соглашениям; Action оправдан координацией проверки, нескольких записей и транзакции.
- [ ] Выполнять разрешение формы, проверку доступности и R03 на серверном пути операции. HTTP-контроллер не должен быть единственным носителем бизнес-инвариантов.
- [ ] В одной транзакции сохранять submission и все его значения. Ошибка на любом значении должна откатывать всё обращение.
- [ ] Определить допустимость формы без обязательных полей и полностью пустого заполнения. Не путать отсутствие обязательных полей с разрешением пустого сообщения без решения R01.
- [ ] Возвращать успех только после успешного сохранения всей операции. Внешний ответ не должен давать доступ к чтению обращения или раскрывать чужие сведения.
