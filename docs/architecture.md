# Архитектура и размещение кода FormFlow

## Статус

Анализ текущего кода (`as-is`) и согласованные правила для нового и изменяемого кода. Правила ниже не означают, что существующий код уже переработан. Перенос классов и изменение поведения выполняются отдельными задачами; существующие исключения не служат образцом для новых зависимостей.

Целевое, ещё не реализованное требование первой версии: изменение определения поля после появления отправок сохраняет предыдущую версию поля и связывает существующие значения с ней. Новые отправки используют текущую опубликованную версию. Конкретная схема хранения и миграции будут определены в задаче реализации; текущее физическое удаление поля каскадно удаляет связанные значения и не удовлетворяет этому требованию.

R02 вводит публичный токен одной формы: случайный 256-битный bearer выдаётся и отзывается только через защищённые операции участнику workspace, в `forms` хранится только его SHA-256 hash. `forms.active` ограничивает публичную доступность. CORS для публичного API разрешает origin из `FORMFLOW_CORS_ALLOWED_ORIGINS` и не использует browser credentials.

## Текущее устройство

По реализации проект представляет собой модульный монолит с разделением на слои и элементами DDD. Модули разделяют ответственность предметной области, но пока не являются изолированными bounded contexts: используют общую БД и напрямую ссылаются на Eloquent-модели друг друга.

| Модуль | Ответственность |
| --- | --- |
| `Identity` | Пользователь, аутентификация, ограничение неудачных попыток входа |
| `Tenancy` | Рабочие пространства, membership, доступ и кеш списков workspace |
| `FormDefinition` | Проекты, формы и определения полей |
| `Submissions` | Отправленные ответы и значения полей |

Расположение `Project` в `FormDefinition` сохраняется: одной связи с workspace недостаточно для переноса в `Tenancy`. Пересматривать границу стоит при появлении самостоятельных сценариев управления проектами вне определения форм.

Подтверждённые особенности:

- [WorkspaceController](../app/Modules/Tenancy/Presentation/Http/Controller/WorkspaceController.php) получает DTO из Form Request и вызывает контракт репозитория; сериализация вынесена в Resources.
- [WorkspaceRepositoryInterface](../app/Modules/Tenancy/Application/Contracts/Repository/WorkspaceRepositoryInterface.php) находится в `Application`, но возвращает Eloquent-модель из `Infrastructure` и Laravel Collection. Поэтому строгая независимость внутренних слоёв сейчас не обеспечивается.
- [WorkspaceRepository](../app/Modules/Tenancy/Infrastructure/Repository/WorkspaceRepository.php) не только сохраняет workspace, но и создаёт membership в одной транзакции. Это уже координация прикладного сценария внутри репозитория. [Тесты](../tests/Feature/Modules/Tenancy/Infrastructure/Repository/WorkspaceRepositoryTest.php) описывают создание обеих записей и откат при ошибке.
- [CachedWorkspaceRepository](../app/Modules/Tenancy/Infrastructure/Repository/CachedWorkspaceRepository.php) расширяет поведение репозитория через декоратор того же интерфейса. Это существующий пример композиции.
- Межмодульные связи двусторонние: [Form](../app/Modules/FormDefinition/Infrastructure/Eloquent/Form.php) ссылается на Submission, а [Submission](../app/Modules/Submissions/Infrastructure/Eloquent/Submission.php) — на Form. Это связано с ORM-навигацией; границы модулей не изолированы на уровне импортов.
- [SubmissionPolicy](../app/Modules/Submissions/Infrastructure/Policies/SubmissionPolicy.php) использует контракт membership из `Tenancy`, а [SubmissionRepository](../app/Modules/Submissions/Infrastructure/Repository/SubmissionRepository.php) фильтрует данные по цепочке ORM-связей до membership. Это две разные обязанности: разрешение операции и ограничение выборки.
- `Domain` пока содержит enum: WorkspaceKind и FieldType. Отдельных прикладных Actions и независимых доменных сущностей в исследованной реализации нет.
- В классах смешаны `final` и открытое наследование. Единой системы точек расширения через наследование не обнаружено.

## Правила развития

Сохранить текущие модули и четыре слоя. Структура подходит текущим сценариям; дополнительная ценность сейчас — в правилах зависимостей и ответственности, а не в переименовании каталогов. Не вводить обязательные domain entities поверх каждой Eloquent-модели, CQRS, шину команд или отдельный пакет на модуль.

### Где создавать код

Пути в таблице относительны к `app/Modules/<Module>`, кроме явно указанных общих каталогов. Не создавать пустые каталоги заранее.

| Задача | Расположение | Граница ответственности |
| --- | --- | --- |
| HTTP-контроллер | `Presentation/Http/Controller` | Принять запрос, вызвать операцию, сформировать HTTP-ответ; имя каталога сейчас в единственном числе |
| Валидация запроса и преобразование в DTO | `Presentation/Http/Requests` | Форма входа, JSON, обязательность и формат полей, `toData()` |
| Формат ответа | `Presentation/Http/Resources` | Публичные поля и сериализация |
| HTTP middleware | `Presentation/Http/Middleware` | Обработка HTTP; интерфейс, зависящий от Request, также может жить здесь |
| Входные данные операции | `Application/DTO` | Типизированные данные; различать отсутствие поля и null, когда это значимо |
| Контракт репозитория | `Application/Contracts/Repository` | Существующая граница сохранения и чтения; сохранять конкретные предметные методы |
| Новый порт интеграции или межмодульной операции | `Application/Contracts` с уточнением по необходимости | Контракт без HTTP-типов и деталей внешнего SDK |
| Сложный или повторно используемый прикладной сценарий | `Application/Actions/<Verb><Subject>Action.php` | Рекомендуемое новое место: координация шагов, вызов правил, граница транзакции; публичный метод `handle()` |
| Предметные значения и правила | `Domain/<Concept>` | Enum, value object или правило, независимое от HTTP, Eloquent и инфраструктурных адаптеров |
| Eloquent-модель | `Infrastructure/Eloquent` | Таблица, связи, casts и локальное поведение модели |
| Реализация репозитория, его декоратор | `Infrastructure/Repository` | Запросы и сохранение, включая ограничения выборки |
| Laravel Policy | `Infrastructure/Policies` | Авторизация; сохраняем существующее размещение |
| Eloquent Observer | `Infrastructure/Observers` | Реакция на жизненный цикл модели; не скрытая координация основного сценария |
| Кеш, адаптер внешнего сервиса, техническая безопасность | `Infrastructure/Cache`, `Infrastructure/Integrations`, `Infrastructure/Security` по назначению | Реализация технической зависимости; Integrations создаётся только при реальной интеграции |
| Очередная задача | `Infrastructure/Jobs` при необходимости | Рекомендуемое место адаптера очереди: вызывает прикладную операцию, не дублирует её правила |
| Миграции, фабрики, seeders | Корневые `database/migrations`, `database/factories`, `database/seeders` | Сохранять текущий механизм загрузки Laravel |
| Тест поведения модуля с Laravel/БД | `tests/Feature/Modules/<Module>/<Layer>/...` от корня | Следовать существующим тестам соответствующего слоя |
| Тест чистого доменного правила | `tests/Unit/Modules/<Module>/Domain/...` от корня, когда появится такое правило | Рекомендуемое место независимых от Laravel тестов |

### Когда нужен Action, а когда достаточно метода

Для простого CRUD сохранять путь `Request → DTO → Controller → Repository → Resource`. Action оправдан, когда операция координирует несколько зависимостей, содержит существенные бизнес-решения или должна одинаково выполняться из HTTP, CLI и очереди. Не создавать его только для переадресации одного вызова репозитория.

Например, `CreateWorkspaceAction` может стать местом координации создания workspace и membership, если сценарий расширяется. Сейчас эта операция остаётся в `WorkspaceRepository::createForUser()`. При последующем выделении необходимо сохранить атомарность, путь декорирования и инвалидирование кеша после commit; использовать существующие регрессионные тесты. Не выполнять такой перенос попутно с несвязанной задачей.

Action может использовать Laravel для транзакции в принятом прагматичном подходе. Чистые предметные правила при этом не должны зависеть от HTTP или БД. Если правило важно и для очереди или CLI, проверка только в Form Request недостаточна: она должна выполняться на общем пути операции. Ограничения целостности БД дополняют такие проверки.

### Зависимости слоёв и модулей

- Новый код в `Domain` не зависит от `Application`, `Infrastructure`, `Presentation` или контейнера Laravel. Для повторяемого правила сначала рассмотреть метод существующего предметного объекта; отдельный сервис нужен, если ответственность не принадлежит одному объекту.
- `Application` описывает операции, данные и необходимые порты; не принимает Form Request и не возвращает HTTP Response/Resource. Новые внешние адаптеры вызываются через контракт. Возврат Eloquent-моделей существующими репозиториями сохраняется как явный компромисс; отдельные сущности и преобразователи вводятся только при конкретной необходимости изоляции.
- `Presentation` отвечает за транспорт, а `Infrastructure` — за реализацию хранения и интеграций. Прикладной сценарий не вызывается через контроллер или Form Request.
- Модуль выбирается по владельцу бизнес-правила и операции. Связь таблиц сама по себе не требует нового модуля; не создавать модуль на каждую сущность.
- Не обращаться к контроллеру или конкретному репозиторию другого модуля для выполнения бизнес-операции. Использовать его прикладной контракт/операцию; узкий порт потребителя допустим, если нужен адаптер к чужой модели. Размещать контракт согласно владельцу операции, без дублирования интерфейсов с одинаковой целью.
- Существующие ORM-связи и запросы через несколько модулей зафиксированы как текущее устройство. Для нового межмодульного взаимодействия использовать публичный прикладной контракт или событие по правилам ниже; не добавлять зависимости от чужих моделей, таблиц и конкретных репозиториев. Существующие связи устранять постепенно в рамках задач, затрагивающих соответствующую границу, с сохранением поведения и проверками.
- Изменять данные другого модуля через его операцию, сохраняя инварианты. Избегать циклов прикладных вызовов, даже когда ORM-связи двусторонние.
- Не создавать общий `Shared`/`Common` для кода с неясным владельцем. Общий компонент оправдан устойчивой одинаковой семантикой у нескольких потребителей.

### Публичная граница модуля

Модуль владеет своими данными и инвариантами. Другие модули обращаются к его публичным прикладным контрактам; расположение класса в `Application` само по себе не делает его публичным API. Явно обозначать предназначенные для других модулей операции в спецификации затронутого сценария.

Новые публичные межмодульные контракты принимают и возвращают идентификаторы, скалярные значения и DTO/снимки результата без Eloquent-моделей, ORM-relations, Builder и HTTP-типов, в том числе во вложенных полях. Публичный DTO может принадлежать модулю-владельцу: зависимость от его согласованного контракта допустима. Внутренний контракт репозитория с Eloquent-типами не становится публичным межмодульным контрактом автоматически. Не создавать domain entity и mapper для каждой модели: для границы достаточно нужного потребителю результата.

Общая БД допустима для модульного монолита; она не даёт разрешения читать и изменять чужие таблицы в новом коде. Разрешённые текущие исключения выше описывают фактическую реализацию, а не целевую границу.

### Вызов, команда или событие

| Требование сценария | Механизм |
| --- | --- |
| Нужны актуальные данные или решение до продолжения операции | Синхронный запрос через публичный контракт владельца |
| Нужно выполнить определённое действие и получить обязательный результат | Явная прикладная операция/команда через контракт; отдельная шина команд не обязательна |
| Нужно сообщить о произошедшем факте для независимых реакций | Событие с названием факта, например `SubmissionCreated` |

Не превращать событие в скрытую команду: если инициатор рассчитывает на конкретного обработчика и его ответ, координация должна быть явной. Обязательные шаги успешной операции не прятать в цепочку подписчиков.

События уменьшают зависимость от реализации получателя, но остаются контрактами. Содержимое события — стабильные идентификаторы и необходимые данные без Eloquent и HTTP-объектов. Изменение payload и смысла учитывать у всех потребителей; версионирование вводить при необходимости совместимости. Не передавать секреты или лишние персональные данные. Событийная интеграция не требует Event Sourcing, CQRS или брокера сама по себе.

Предлагаемые места при появлении событий: внутренние чистые предметные факты — `Domain/<Concept>/Events`, публичные межмодульные факты — `Application/Events` модуля-источника. Обработчик реакции принадлежит модулю-потребителю: координация в `Application`, адаптер Laravel/очереди в `Infrastructure/Listeners` или `Infrastructure/Jobs`. Внутреннее доменное событие не становится публичным автоматически; преобразование нужно только при различающихся контрактах. Эти каталоги пока являются правилами размещения, а не описанием реализованной событийной системы.

### Согласованность и доставка

Для каждого нового межмодульного сценария фиксировать требуемую актуальность данных, границу успешного завершения и поведение при ошибке зависимости. Особенно различать обязательный результат записи и отложенную реакцию на неё.

- Проверки доступа требуют актуального решения `Tenancy`. Не заменять их отстающей проекцией membership без отдельно согласованной модели отзыва доступа. Существующие ограничения выборки сохранять при переходе на контракт: одной проверки policy недостаточно.
- Синхронные обработчики событий выполняются в том же вызове и сохраняют зависимость от ошибок и времени выполнения обработчика. Не считать их независимой доставкой; при использовании общей транзакции явно определить, что должно откатываться.
- Асинхронные реакции допускают временное рассогласование. Определить политику повторов, идемпотентность, поведение при окончательном сбое и требования к порядку событий. Не предполагать однократную доставку или общий порядок обработки без соответствующих гарантий.
- Уведомления о сохранённых изменениях публиковать только после успешного commit; при rollback их быть не должно. Это правило не запрещает внутренние доменные события в транзакции. Публикация после commit сама по себе не закрывает сбой между сохранением данных и отправкой сообщения.
- Если потеря асинхронного события недопустима, применять надёжную публикацию, например transactional outbox с записью события в одной транзакции с данными и повторяемой доставкой. Не внедрять outbox, брокер и инфраструктуру доставки для каждого события заранее.

### Пересмотр границ

Модули не обязаны повторять структуру будущих микросервисов. Частые взаимные прикладные вызовы или постоянная потребность в общей транзакции — повод проверить ответственность и границы модулей. Сначала рассмотреть объединение связанного сценария или перенос ответственности; не вводить саги и цепочки событий только ради сохранения первоначального деления.

Изоляция подтверждается фактическими зависимостями и проверками, а не названиями каталогов. Для нового взаимодействия проверить импорты, доступ к данным и содержимое контрактов. Когда риск повторного нарушения оправдывает автоматизацию, добавить узкую архитектурную проверку разрешённых зависимостей с явными исключениями для текущего кода; не выдавать такую защиту за уже существующую.

### Расширяемость и размер классов

Расширяемость означает возможность добавить нужное поведение через понятную точку изменения: зависимость, реализацию контракта, композицию или обоснованное наследование.

- Сначала выбирать композицию и внедрение зависимостей. Декоратор репозитория с кешем — подходящий пример расширения без изменения потребителей.
- Сохранять контракты репозиториев. Для остальных классов вводить интерфейс при наличии границы интеграции, стратегии, декоратора или необходимости подмены зависимости с содержательным поведением. Вторая реализация не обязательна, но одной возможности написать интерфейс недостаточно.
- Не делать все классы наследуемыми автоматически. `final readonly` подходит DTO; `final` допустим для реализаций, расширяемых через контракт или композицию. Если требуется наследование, не закрывать выбранную точку расширения `final`, явно описать контракт переопределения и проверить базовое поведение. Не убирать `final` массово.
- Не открывать все поля и методы через `protected` на будущее. Использовать минимальную видимость; точка переопределения должна иметь конкретного потребителя или подтверждённое требование.
- Небольшой класс имеет связную ответственность. Разделять его при независимых причинах изменения, сложных ветках с отдельными правилами или повторении существенной логики; количество строк само по себе не критерий.
- Не создавать `BaseRepository`, универсальный CRUD-сервис, пустые интерфейсы, сервисы-переадресаторы или наследование только ради нескольких одинаковых строк. Короткий вспомогательный метод часто достаточен.

### Подключение и проверка

Репозитории подключаются в `app/Providers/RepositoryServiceProvider.php`, policies и observers — в `AppServiceProvider`, зависимости HTTP middleware — в `PresentationServiceProvider`. Для нового типа инфраструктуры выбрать подходящий provider по его ответственности; не складывать все bindings в provider репозиториев.

Применять `formflow-feature` для реализации, `formflow-api-contract` для HTTP, `formflow-tenancy` для доступа и кеша, `formflow-testing` для проверок. При переносе сценария сохранять авторизацию, ограничения выборки, транзакционность и жизненный цикл побочных эффектов. Размещение класса само по себе не подтверждает безопасность или корректность операции.

## Основания рекомендаций

- [Bounded Context — Martin Fowler](https://martinfowler.com/bliki/BoundedContext.html): контексты задаются границами моделей и явными отношениями между ними. Наличие четырёх каталогов само по себе не доказывает изоляцию контекстов.
- [Service Layer — Patterns of Enterprise Application Architecture](https://martinfowler.com/eaaCatalog/serviceLayer.html): прикладной слой координирует операции и транзакции. Это основание для постепенного выделения сложных сценариев.
- [Laravel 13: Service Container](https://laravel.com/docs/13.x/container): внедрение зависимостей и привязка интерфейсов к реализациям поддерживают выбранный механизм расширения.
- [What do you mean by “Event-Driven”? — Martin Fowler](https://martinfowler.com/articles/201701-event-driven.html): события, перенос состояния и риск скрытых команд и цепочек управления.
- [Domain events: Design and implementation — Microsoft](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation): границы внутренних и интеграционных событий, согласованность и успешное сохранение данных.
